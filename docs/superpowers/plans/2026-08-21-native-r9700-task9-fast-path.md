# Native R9700 Task9 Fast Path Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a real R9700-backed, atomic 16-layer Llama 3.2 1B fp16 KV NPZ that the existing native worker accepts, without restoring the retired source-as-data proof lane.

**Architecture:** Reuse the current product AMDev resident-dispatch seam, C0A25 PM4/SDMA/fence mechanics, and real safetensors span binder. Generate and review a fresh, file-backed kernel asset catalog for a minimal complete Llama stage set; bind real token/model buffers, execute stage kernels resident on the R9700, and emit K/V only after all layers complete. Existing `kv_cache.py`, `parity.py`, and `serving.py` remain consumers; no cache schema or network work is added.

**Tech Stack:** Python 3.12.8, pytest, C++17, macOS `xcrun --sdk macosx clang++`, TinyGPU.app / APLRemotePCIDevice / PCIIface, AMD gfx1201, safetensors, existing local Llama 3.2 1B MLX model.

## Global Constraints

- Use `${HOME}/.pyenv/versions/3.12.8/bin/python3`; never `python3` from PATH.
- Target Llama 3.2 1B fp16 first: 16 layers, 8 KV heads, head dim 64.
- `r9700_native` accepts only real R9700 model-forward work. CPU may validate/serialize/compare but never provides accepted tensor math.
- Preserve S-1 cache semantics: producer owns prefix K/V; mlx-lm receives only the final prompt token.
- Preserve NPZ and prompt-cache schema. Do not change `kv_cache.py` tensor naming/metadata rules.
- Do not restore, compile, link, parse at runtime, copy from, or depend on the archived `c1_primitive_bridge.cpp` proof artifacts. They are forensic evidence only.
- Do not add a generic ROCm layer, network transport, build system, benchmark work, Qwen support, or native consumer backend.
- Every production kernel asset must be fresh, file-backed, digest-bound to descriptor code, independently reviewed, and tied to real model/token input provenance. Fixture bytes and expected outputs are prohibited as runtime operands.
- Hardware runs are supervisor-owned, serialized, and occur only after no-hardware contracts, source review, and explicit build success.
- Fast path means one minimal complete vertical slice and one actual hardware acceptance run; it does not mean primitive-proof expansion, exhaustive microkernel proofs, or speculative performance work.

## Plan Self-Review

- **Coverage:** Tasks 1–7 cover the current missing asset/layout blocker through a real full producer; Tasks 8–9 cover the already prepared parity/serving gates.
- **Speed:** Starts with one compiler capability gate, then parallelizes independent asset/layout/binder preparation. It avoids archive archaeology, exhaustive primitive proofs, benchmarks, and unrelated targets.
- **Fail-closed:** Every gate requires real model/tokens/assets/hardware evidence. No task permits CPU math, fixture operands, archive reuse, or a pass claim without a full result.
- **Consistency:** All consumers retain the existing KV NPZ and S-1 prompt-cache contracts.
